# Application Design Document — Bulls and Cows Game

## 1. Data Structures & State Management

The application strictly adheres to the Functional Programming (FP) paradigm. No object-oriented classes or mutable states are used.

### Game State

The internal game state is managed by a single immutable configuration object (`GameState` interface) containing the following fields:

- `length` (number): Length of the secret code (2–6).
- `base` (GameBase): Selected number system (2, 8, 10, or 16).
- `secretNumber` (string): The secret code generated by the computer.
- `history` (Array of objects): An ordered sequence of user attempts. Each entry records the guess string, calculated bulls/cows count, and the round elapsed time.
- `isWon` (boolean): Flag identifying the completion status of the round.
- `startTime` / `elapsedTime` (numbers): Used for tracking the game clock.

### Immutability Implementation

State updates never perform direct object modifications or array insertions (e.g., using `.push()`). Instead, functions return entirely new records leveraging the shallow copy spread operator (`[...]` and `{...}`), fulfilling the rigid constraints of immutable programming. To maintain strict purity, dynamic metrics like timestamps are calculated externally and passed into state reducers as arguments.

## 2. Core Algorithms Analysis

### evaluateGuess

The algorithm maps over the player's guess sequence using array methods to prevent sequential loop counters:

1. **Bulls:** Evaluated using `.filter()` by matching elements where the position index and value in the guess array are strictly equal to the secret string.
2. **Cows:** Evaluated by checking character matches present inside a pre-built `Set` of the secret number to guarantee linear execution, using the mathematical logic: `cows = totalMatches - bulls`.

### countPossibleSecrets

This function computes the partial permutation formula $P(n, k) = \frac{n!}{(n-k)!}$ using direct linear recursion. To optimize performance and prevent repeated tree evaluations when opening settings screens, a standard memoization technique is implemented using a global `Map`. The computed lengths and bases serve as hash keys; matches yield immediate cache results.

## 3. Computational Complexity (Big O)

- **`generateSecret(length, base)` — $O(base)$**
  The algorithm generates an alphabet array of size equal to the `base`. It shuffles the alphabet using the Fisher-Yates algorithm, running a single linear `for` loop from the maximum index down to 1. Since array element swaps occur in constant $O(1)$ time, the time complexity scales linearly with the alphabet size of the number system. Truncating the array to the requested `length` takes $O(length)$ time, which is tightly bounded by the base size.

- **`evaluateGuess(secret, guess)` — $O(length)$**
  The guess string is split into an array of size equal to `length`. Creating a native `Set` from the secret takes $O(length)$ time. The subsequent `.filter()` iterations evaluate membership checks against the `Set` in constant $O(1)$ time. This avoids nested scan routines and yields a strictly linear $O(length)$ total time complexity.

- **`isValidGuess(guess, length, base)` — $O(length)$**
  Validating lengths and building a unique character `Set` takes linear time relative to the number of digits. Invoking the curried digit validator checks membership against a sliced alphabet string of size `base`. Since the maximum base is structurally bounded (constant maximum of 16), the validator runs in effectively $O(1)$ time per digit. Thus, the total complexity scales linearly with the input size.

- **`countPossibleSecrets(length, base)` — $O(length)$ without cache / $O(1)$ with cache**
  The recursive execution stack decrements the `length` property by exactly 1 at each frame down to the base case of 0, yielding a linear depth of $O(length)$. With memoization active, subsequent lookups hit the internal `Map` instantly, dropping the call time to a constant $O(1)$ complexity.

## 4. Clean Code Principles Applied

- **Single Responsibility Principle (SRP):** Core logical evaluations are explicitly split into focused utilities. For example, `createDigitValidator` handles exclusively single-character domain constraints, while `isValidGuess` coordinates whole input flows.
- **Pure Functions & No Side-Effects:** Core game computations do not rely on global references or window DOM hooks. Side-effect engines, such as random generation sources, are explicitly passed as functional parameters, making the core perfectly isolated and deterministic for testing runners.
- **KISS (Keep It Simple, Stupid):** The character checking module circumvents heavy regex parsing matrices or unsafe type coercion. It leverages a clean declarative sub-alphabet extraction `slice(0, base)` and validates characters using the simple native `.includes()` method.
- **Self-Documenting Code:** Explicit naming architecture ensures functions clearly state intents (e.g., `countPossibleSecrets`, `evaluateGuess`) eliminating the need for cryptic code or heavy inline comment overheads.
